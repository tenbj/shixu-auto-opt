# 账号与远程接入 · 3.1

本说明取代2.x关于共享工作台、无账号API和文件密钥发放的操作。正式界面对应 accounts v8 原型。

## 日常使用

每个账号独立保存问题、行动、身份、编号、审计和回收站。账号归属由服务器认证决定，请求不能指定owner。历史记录全部归到test；人类发起者、工具及模型快照保留。新账号从空工作台开始。

桌面和手机右上角保留头像、姓名、独立工作台的账号卡片。下拉包含账号设置、AI接入、工作台工具、退出登录。工作台工具使用可返回的二级菜单。设置和MCP为弹窗，内部Tab切换，关闭保留页面和筛选。左侧只保留业务导航。

## 新电脑怎样连接

支持OAuth的MCP客户端填写HTTPS的 `/mcp` 地址，在浏览器登录自己的拾序账号，检查客户端和权限后授权。服务器或不支持OAuth的客户端，登录网页 → 右上角账号 → AI接入 → 手动配置 → 访问令牌 → 命名并选择只读/读写 → 生成配置。复制或下载到目标设备私有目录即可，新设备不需要源码或发放脚本。

```json
{"mcpServers":{"shixu":{"type":"http","url":"https://你的域名/mcp","headers":{"Authorization":"Bearer <网页生成的令牌>"}}}}
```

令牌只在生成时显示，数据库仅保存摘要。PAT有效期1年，OAuth令牌1小时；OAuth提供最长30天的轮换refresh_token，绑定client_id/resource；刷新保留授权ID并替换旧访问令牌；已消费刷新令牌重放撤销整个授权族。每次请求校验所属账号、有效期、撤销及read/write范围，令牌不能管理账号。我的设备支持重命名、单独撤销，显示最近访问和真实MCP验证时间，不能以最近访问声称设备在线。退出撤销当前网页登录会话；修改密码撤销全部网页登录会话；MCP授权需单独撤销。

OAuth支持公共客户端动态注册、authorization_code、S256 PKCE、严格回调、resource绑定及一次性授权码。固定协议验证不代表每种客户端已实测；不兼容时使用PAT配置。

## 服务端升级与部署

从2.4升级前停止服务，在进程环境提供 `SHIXU_BOOTSTRAP_PASSWORD`，执行 `python scripts/migrate_accounts.py`。清除该临时变量后启动。初始密码不写入源码和项目包。脚本先保存私有数据库快照，再追加账号表/owner、调整账号内唯一键，并逐表比对原有列。MySQL DDL无法整体事务回滚；故障保留备份，修复后补齐，恢复旧数据应在独立库核对。

2.x全局密钥文件不再被接受，迁移后登录网页重新发放。不能依靠旧脚本生成全局密钥或向其他账号复制身份ID。

支持HTTP与HTTPS：默认只允许HTTPS及本机回环认证；部署设置 `SHIXU_ALLOW_HTTP_AUTH=true` 后，公网HTTP可登录、管理账号及生成/撤销PAT，并通过API/MCP读写当前账号工作台。HTTP明文传输密码、会话、令牌与业务数据。标准远程OAuth仍要求HTTPS；HTTP页面引导使用手动配置 → 访问令牌，该令牌也适用于个人电脑客户端。

MCP优先使用SHIXU_PUBLIC_URL中配置的HTTPS入口，客户端授权说明和PAT下载配置保持一致，即使网页是通过HTTP或本机打开。未配置HTTPS规范地址时才使用当前访问地址；配置HTTP地址不会将HTTPS请求降级。已有HTTP令牌配置仍可继续使用，不自动重写已有私有文件。HTTP与HTTPS使用独立会话Cookie，HTTPS使用Secure及__Host-前缀，不接受HTTP会话作为HTTPS登录；切换协议需重新登录，各自退出不影响另一协议的独立会话，改密码仍撤销全部网页登录会话。

开放HTTP不会创建HTTPS监听或证书。接入HTTPS反向代理时，配置 `SHIXU_ALLOWED_HOSTS`、按需设置OAuth规范地址 `SHIXU_PUBLIC_URL`。服务脚本默认不信任代理头；仅在实际HTTPS代理覆盖转发头、且后端只可由该代理访问时设置 `SHIXU_TRUSTED_PROXY_IPS` 为具体代理IP。纯TCP穿透保持空值；不能将FRP出口IP当作可信TLS代理，避免客户端伪造X-Forwarded-Proto。反向代理须保留外部Host和端口，正确设置协议头。不要为同时支持HTTP而删除HTTPS Cookie的Secure属性。

API/Python和本机stdio从私有环境变量 `SHIXU_MCP_TOKEN` 读取令牌。stdio需要本机源码及 `SHIXU_API_URL`，远端优先HTTPS的Streamable HTTP传输。HTML示例先在同源系统登录，再读取当前会话CSRF。凭据不能进入代码库、Skill正文、日志和分发包。

401重新授权；403检查只读范围或CSRF；404也可能是对象属于其他账号；409重新读取当前账号revision；结果未知时保留原request_id和参数重试。创建来源仍需传creation和实际模型，认证账号不代替创建人快照。

本版无管理员角色、共享工作台或密码找回；可通过 `SHIXU_ALLOW_REGISTRATION=false` 关闭注册。单机交付，未做高可用/大负载认证；数据库连接尚未启用TLS。

## 同时保留公开HTTP与HTTPS的TCP穿透

公开HTTP和Caddy HTTPS共用FRP路径时，不能简单信任FRPC出口的X-Forwarded-Proto。可配置私有SHIXU_HTTPS_PROXY_SECRET（至少32字符随机值）及标准443的SHIXU_PUBLIC_URL，保持SHIXU_TRUSTED_PROXY_IPS为空。Caddy HTTPS站点须覆盖X-Shixu-HTTPS-Proof为相同秘密，并覆盖X-Forwarded-Proto为https。服务验证单一标记、协议和准确公网Host后才按HTTPS处理，并移除该标记；未认证协议头仍按HTTP。

该标记属于部署秘密，不是账号令牌，不应交给客户端或提交仓库。私有Caddyfile保存在application/private/caddy-https/，只复制到实际HTTPS网关，勿开启会记录秘密请求头的调试日志。HTTPS识别与浏览器到网关加密分别验证，FRP隧道另核对。HTTP/HTTPS的会话Cookie保持独立；开启HTTP认证的明文传输特性不改变。
